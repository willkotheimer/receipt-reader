Project Governance Document: The Receipt ReaderDocument Version: 1.0.1Status: ActiveTarget Platform: Azure AI Document Intelligence (prebuilt-receipt), React, ASP.NET CorePrimary Execution Engine: Claude Code / Autonomous CLI Pipeline1. Project Purpose & Ephemeral Architecture PrinciplesThe Receipt Reader is a lightweight proof-of-concept visual showcase demonstrating secure, zero-trust cloud vision processing.Core Architectural AxiomsZero Server Persistence: Receipts are processed strictly in-memory (Stream). The server-side layer MUST NOT write, cache, or persist image buffers or extracted data payloads to disk, blob storage, or databases.Client-Bound Storage Only: Extracted receipt arrays exist only in browser memory and localStorage.Graceful Fail-Closed Error Handling: Non-receipt payloads or low-confidence parsing attempts return a uniform 400 Bad Request with an uninformative "Unable to process document." string to mitigate reverse engineering and trolling attempts.2. Detailed Governance Clauses§2 Data ScaffoldRules: The client data shape (React Query cache keys, Reactstrap table models) and the C# API response DTOs must maintain strict 1:1 parity with the Azure Document Intelligence prebuilt-receipt contract fields (MerchantName, TransactionDate, Total, Tax, Items).Enforcement: A CI schema verification step compares TypeScript interfaces against C# DTO contracts on every pull request. Mismatches without a recorded Architecture Decision Record (ADR) tag fail the build immediately.§3 Departure ProtocolRules: Any architectural deviation from this governance document (such as adding temporary blob logging or changing error response structures) requires an ADR entry in /docs/adr/.Enforcement: Pre-commit hooks parse git commit messages and PR bodies for Governance-Ref: tags and block approval if no matching ADR markdown file is present.§4 TraceabilityRules: Every API route, TanStack Query hook, and xUnit test class must link back to a specific governance section or user story ID via inline attributes/docstrings ([GovernanceRef("SECTION-3")]).Enforcement: Custom ESLint and Roslyn analyzers flag any unreferenced public functions or API endpoints.§5 Findings RegisterRules: Security or quality defects identified during code reviews or automated scans must be logged in the project FINDINGS.md registry.Enforcement: PR merge approvals are blocked until all logged findings have corresponding closing unit or integration test signatures attached.§6 TDD ExecutionRules: Development must follow strict Red-Green-Refactor cycles.Enforcement: CI workflow verifies git commit history. Every feature branch must contain a commit where test files (Vitest or xUnit) were modified or added prior to or separately from the passing implementation code commit.§7 AI Safeguards (Claude Code & Copilot Execution)Rules: AI-generated tests must include meaningful assertions. Tests containing zero assertions, dummy passes, or unhandled async mocks are prohibited.Enforcement: CI coverage tools (Coverlet for C#, Vitest coverage for TS) evaluate branch execution paths and fail on unhandled async promises or mock-only passes.§8 Scope & Actions (Sandboxing)Rules: Local build environments and CI containers operate under strict least-privilege principles. The application runtime cannot invoke external network endpoints beyond the designated Azure Document Intelligence resource URI.Enforcement: Sandbox network policies restrict outbound HTTP calls to explicitly whitelisted domain patterns.§9 Technology Stack & Testing Mandates                             [ React Frontend ]
